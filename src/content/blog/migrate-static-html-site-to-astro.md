In this project, we migrated a 35-page static HTML site to Astro content collections — and rewrote the daily publishing script that used to patch that HTML by hand. This guide walks through the same sequence: lock the URL shape, move content into collections, lift shared markup into layouts, generate routes from data, rewrite the tooling, and verify against the old output before cutting over.

Astro's documentation positions this kind of site — blogs, landing pages, marketing pages — as "ideally suited" for conversion, and notes you can often keep existing stylesheets and Markdown content. See [Migrate an existing project to Astro](https://docs.astro.build/en/guides/migrate-to-astro/).

## What we migrated

The site (Couple in Bond) shipped as plain files: two hand-maintained index pages, 17 poll detail pages, and 16 companion articles. A Python script generated two new polls a day by string surgery on those files — inserting cards into index pages, duplicating a detail-page template, patching JSON-LD blocks, and editing the sitemap by hand.

![Repository tree before the migration: `polls/` with 17 hand-written HTML pages, `blog-posts/` with 16 companion articles, and shared scripts at the root](/article-media/migration-source-tree.png)

After the migration, the same build produces 35 pages from:

- Markdown files with YAML frontmatter under `src/content/polls/` and `src/content/blog/`
- Two Astro layouts that render head tags, Open Graph/Twitter cards, and JSON-LD
- Dynamic routes generated by `getStaticPaths()`
- Index pages that rebuild card grids and `ItemList` JSON-LD from the collections
- A generator that writes Markdown instead of patching HTML (the script shrank by 107 lines)

## Before you start

This guide assumes a static site (no framework), a build step you control, and content that repeats a page template. It does not cover porting a React or Vue app — Astro supports those components directly, but that is a different migration. We used Astro 6 with TypeScript; the content schema below needs `@ts-check` or a `tsconfig` for full typing, but works in plain JavaScript projects too. The layout examples build on the shared-layout pattern from our [responsive Astro blog layout guide](https://www.techtips.fun/blog/create-astro-site-responsive-layout/).

## Step 1: Lock in the existing URL shape

Astro's default build emits directory-style URLs (`/polls/weekly-ritual/`). Every existing link, canonical tag, sitemap entry, and indexed URL on the old site used `.html` suffixes, so the first configuration decision was to preserve them:

```js
// astro.config.mjs
export default defineConfig({
  site: 'https://couplein.bond',
  build: {
    format: 'file', // emits /polls/weekly-ritual.html, not /polls/weekly-ritual/
  },
});
```

Decide this before writing any content, because the layouts compute canonical URLs from it. If your old site already uses clean URLs, you can skip this step.

## Step 2: Move page content into collections

Content collections let Astro treat Markdown files as typed records. Each page's unique fields — title, description, options, related links, ordering — move into YAML frontmatter, and the repeated shell moves into a layout. Astro's [Markdown in Astro](https://docs.astro.build/en/guides/markdown-content/) guide covers frontmatter basics; the [content collections guide](https://docs.astro.build/en/guides/content-collections/) covers the collection layer.

First, define the collections and their schemas in `src/content.config.ts`:

```ts
import { defineCollection, z } from 'astro:content';
import { glob } from 'astro/loaders';

const polls = defineCollection({
  loader: glob({ pattern: '**/*.md', base: './src/content/polls' }),
  schema: z.object({
    question: z.string(),
    pageTitle: z.string(),
    description: z.string(),
    intro: z.string(),
    topic: z.string(),
    slug: z.string(),
    listOrder: z.number(), // index ItemList position
    ogImage: z.string(),
    options: z.array(z.string()).default([]),
    related: z.array(z.object({ href: z.string(), title: z.string() })).default([]),
    draft: z.boolean().default(false),
  }),
});

export const collections = { polls };
```

Then convert each HTML page to a Markdown file. A migrated poll page looks like this:

```yaml
---
question: "What should a couple make time for this week?"
pageTitle: "What should a couple make time for this week?"
description: "A weekly relationship poll about simple rituals that help couples slow down, reconnect, and enjoy time together."
intro: "A good weekly ritual is realistic enough to repeat and meaningful enough to look forward to."
topic: "Connection"
slug: weekly-ritual
listOrder: 3
ogImage: "https://couplein.bond/assets/polls/weekly-ritual-share.jpg"
options:
  - "A tech-free meal"
  - "A walk with no agenda"
related:
  - href: "connection-ritual.html"
    title: "What helps two people feel most connected?"
draft: false
---
```

### Give every collection a schema that fails the build

The zod schema is not decoration. On the old site, a missing meta description silently shipped an empty tag. With the schema above, a Markdown file missing `description` fails `npm run build` instead. Required fields should be `z.string()` with no default; anything genuinely optional gets `.optional()` or `.default()`.

Here is that failure in practice — a test page with its `description` frontmatter removed, validated against the schema:

## Step 3: Move shared chrome into layouts

Every detail page shared the same head: title pattern, meta description, canonical, robots, stylesheets, deferred scripts, OG/Twitter tags, and a JSON-LD graph. That shell became `src/layouts/PollDetail.astro`, which receives the collection entry and renders everything from frontmatter:

```astro
---
const { poll } = Astro.props;
const d = poll.data;
const url = `${SITE}/polls/${poll.id}.html`;

const graphLd = {
  '@context': 'https://schema.org',
  '@graph': [
    { '@type': 'WebPage', url, name: d.question, description: d.description },
    {
      '@type': 'Question',
      name: d.question,
      text: d.question,
      answerCount: d.options.length,
      suggestedAnswer: d.options.map((text) => ({ '@type': 'Answer', text })),
    },
    // BreadcrumbList: Polls › this question
  ],
};
---
<script type="application/ld+json" set:html={JSON.stringify(graphLd)}></script>
```

Google documents JSON-LD as a structured-data format its systems can read, so emitting the same graph from a layout preserves the old pages' search markup rather than approximating it. See [Google's introduction to structured data](https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data).

The body markup stayed deliberately plain: the voting form is still hydrated by the site's existing `poll-detail.js`, served from `public/`. Astro copies `public/` verbatim into the build, so client-side behavior (voting state in localStorage) was untouched without rewriting it as a framework component.

## Step 4: Generate detail pages from the collection

With content and layout in place, one dynamic route replaces 17 hand-written HTML files:

```astro
---
import { getCollection } from 'astro:content';
import PollDetail from '../../layouts/PollDetail.astro';

// Emits polls/<id>.html because astro.config.mjs sets build.format: 'file'
export async function getStaticPaths() {
  const polls = await getCollection('polls');
  return polls.map((poll) => ({
    params: { slug: poll.id },
    props: { poll },
  }));
}

const { poll } = Astro.props;
---
<PollDetail poll={poll} />
```

`getStaticPaths()` tells Astro which pages to prerender at build time; the [Astro API reference](https://docs.astro.build/en/reference/api-reference/#getstaticpaths) documents the full contract. The same pattern with the `blog` collection and a `BlogPost` layout replaced the 16 companion articles.

## Step 5: Regenerate index pages from the same data

The old index pages were the riskiest files: hand-patched cards, hand-numbered JSON-LD positions, and a grid that sorts by recency in the opposite direction from the list. Both index pages now derive everything from the collection:

```astro
---
const polls = (await getCollection('polls'))
  .filter((p) => !p.data.draft)
  .sort((a, b) => a.data.listOrder - b.data.listOrder);

const ld = {
  '@context': 'https://schema.org',
  '@graph': [
    // CollectionPage and ImageObject entries…
    {
      '@type': 'ItemList',
      itemListOrder: 'https://schema.org/ItemListOrderAscending',
      numberOfItems: polls.length,
      itemListElement: polls.map((poll, i) => ({
        '@type': 'ListItem',
        position: i + 1,
        name: poll.data.question,
        url: `${SITE}/polls/${poll.id}.html`,
      })),
    },
  ],
};
---
```

One subtlety worth calling out: our blog content carries three independent rank fields — `cardOrder` (the grid sorts descending, so the newest card must get the highest value), `ldOrder` (the ItemList sorts ascending), and `listOrder` (the polls index sorts ascending). A single "position" field cannot serve both sort directions; if your index pages sort differently, model each rank separately from day one.

## Step 6: Rewrite the tooling that patched HTML

The daily generator was the biggest win. Its old job was HTML surgery; its new job is writing content files. Two helpers did most of the work:

```python
def yaml_value(val):
    """json.dumps output (double-quoted strings, flow lists)
    is valid YAML, so quotes, colons and unicode in titles
    cannot break frontmatter parsing."""
    if isinstance(val, bool):
        return "true" if val else "false"
    if isinstance(val, (int, float)):
        return str(val)
    return json.dumps(val, ensure_ascii=False)

def next_orders():
    """Next cardOrder/ldOrder (blog) and listOrder (polls): max + 1 each."""
    # cardOrder: the blog grid sorts descending, so max+1 prepends a card
    # ldOrder:   the blog ItemList sorts ascending, so max+1 appends
    # listOrder: the polls index sorts ascending, so max+1 appends
```

Encoding values with `json.dumps` matters because poll titles contain quotes, colons, and curly apostrophes that break naive YAML. And because the three rank fields sort in different directions, the generator computes each as `max(existing) + 1` — for the descending grid, that deliberately hands the first companion in a batch the top card slot.

Two more guardrails from the implementation:

- A `validate_frontmatter()` check runs before any commit: every generated Markdown file must open and close with `---` fences and contain each required key, or the run aborts.
- A `poll_history.json` file records every id ever used, so re-running the generator for the same date never duplicates content. Commit that file — losing it breaks idempotency.

## Step 7: Verify before cutover

We verified against the old site's output, not just the new build:

- `npm run build` produced 35 pages — the expected route count (17 polls + 16 companions + 2 index pages).
- The project's regression scripts check generated HTML against the original pages' head tags, JSON-LD, and markup: `verify_index.py` reported 21/21 checks on both index pages, and `verify_poll.py` reported 32/32 on a sample detail page.
- As a full rehearsal, we ran the generator for a future date (2 polls + 2 companions), rebuilt, and ran a temporary verifier covering 54 assertions — new page structure, JSON-LD, both index grids and ItemLists, sitemap entries, and cross-links. All 54 passed. We then reverted the rehearsal files with `git checkout` before merging.
- After cutover, a fresh audit compared the original static files against the live site: all 33 detail pages pass 138/138 checks (title, description, canonical, JSON-LD), and both index pages pass their head-tag checks.

![Post-cutover audit output: 33 of 33 detail pages pass all 138 checks — title, description, canonical, and JSON-LD — and both index pages pass every head-tag check](/article-media/migration-verify-live.png)

Treat rehearsal output as disposable: label test runs clearly, and use `git status` to confirm which files are new. In our repo, one cleanup pass wrongly deleted legitimately migrated pages that looked like test artifacts; they were restored from git, but the near-miss is why the final rehearsal was reverted with `git checkout` rather than `rm`.

## Step 8: Cut over and deploy

The merge was where the old and new sites collided — and it resolved cleanly. The old index HTML had been modified on `main` while the migration branch deleted those files, and the static detail pages added by the old generator were removed in favor of the generated routes. The final merged tree differed from the migration branch by exactly one file: the generator's history log.

Deployment configuration pointed the host at the new build:

```json
{
  "framework": "astro",
  "buildCommand": "npm run build",
  "outputDirectory": "dist"
}
```

The live result: a poll detail page and the companion-article index, rendered from the collections:

## Common problems and fixes

Observed during this migration:

1. **Frontmatter breaks on titles with quotes or colons.** Encode values as JSON — JSON strings and flow lists are valid YAML.
2. **A missing field ships an empty tag.** Make required fields non-optional in the zod schema so the build fails instead.
3. **URLs silently change from `/x.html` to `/x/`.** Set `build.format: 'file'` before migrating content.
4. **The new card lands at the bottom of the grid.** Check each order field's sort direction; a descending grid needs the highest value for the newest card.
5. **Merge conflicts on the old HTML at cutover.** Resolve by deleting the HTML files; the generated routes own those URLs now.
6. **Re-running the generator duplicates content.** Keep the idempotency history file committed.

## Pre-launch checklist

- Build page count equals the expected route count
- Spot-check generated HTML: title, description, canonical, OG/Twitter tags, JSON-LD
- Index grids and ItemLists match the old pages' counts and ordering
- Sitemap lists every route
- Client assets still load from `public/`
- Regression scripts pass on sample pages
- Desktop and narrow-viewport previews show no overflow or clipped text

## Conclusion

The transferable pattern is simple: content into collections with a strict schema, shared chrome into layouts, routes generated from data, and tooling that writes content instead of patching HTML. The trade-off is that Markdown and frontmatter are less WYSIWYG than hand-edited HTML — but the schema turns silent content gaps into build errors, and the generator shrank by 107 lines while gaining the same guarantees. If you run an Astro blog, the same collection approach also powers [category and tag archives](https://www.techtips.fun/blog/how-to-create-categories-and-tags-in-an-astro-blog/).
